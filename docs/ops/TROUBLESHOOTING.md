# Sign2Text Troubleshooting Guide

This guide covers the most common operational issues in the current Sign2Text stack and points back to the implemented startup and routing behavior.

## 1. Startup And Launcher Issues

### `start.py` fails to launch

- Port conflict: check whether ports `5500`, `8000`, `8001`, `8002`, `8003`, or proxy port `8080` are already in use.
- Python version: use Python `3.11+`.
- Runtime dependencies: prefer the repo scripts so the right dependency set is installed.

Recommended recovery:

```powershell
.\setup.ps1
.\start.ps1
```

Manual dependency recovery:

- CUDA path: `pip install -r requirements.runtime.txt`
- CPU path: `pip install -r requirements.runtime-cpu.txt`

### `runtime-config.js` changes keep disappearing

- `frontend/runtime-config.js` is generated by `start.py` on each launch.
- Do not edit that file manually.
- Change `.env`, `backend/.env`, or the relevant environment variables instead.

## 2. Interface And Routing Confusion

### "I am seeing the landing page instead of the app"

- This is expected when `landing/dist/index.html` exists.
- Open the main app directly at `/index.html`.

### "I am seeing the app instead of the landing page"

- The landing site is only served when `landing/dist/index.html` exists.
- Rebuild the landing app if you expect `/` to serve the React site.

### "Proxy mode works for `/index.html`, but my landing forms fail"

- The main app and admin page use generated `runtime-config.js` and follow `/admin-api` in proxy and tunnel mode.
- The landing site still relies on build-time `landing/src/config.js`, not generated runtime config.
- In the current source, production builds target `/admin-api`. If landing forms are still failing, the deployed `landing/dist` is likely stale.
- Rebuild the landing app from `landing/` with `npm ci` and `npm run build` (not from the repo root), then redeploy or re-serve the refreshed `landing/dist`.

## 3. ASL And Letter Mode

### Infinite loading or "backend not reachable"

- Verify that the ASL service is running on port `8000` and the Letter service is running on port `8002`.
- In proxy mode, verify the prefixed routes such as `/asl-api/status` and `/letter-api/health`.
- If you are using a non-default origin, ensure the relevant CORS settings include your browser origin.

### "No camera found"

- The current ASL and Letter flows default to browser-camera capture with frame upload to the backend.
- Check the browser's camera permission prompt first.
- Only troubleshoot backend-local camera access if you intentionally switched away from the default browser-upload path.

### ASL starts but does not produce English output

- Verify the Ollama endpoint, model, and timeout configuration.
- If you launched with `.\start.ps1 -NoOllama`, this is expected: ASL recognition still runs, but output remains in raw gloss form.

## 4. Authentication (All Modes) And Voice

### Authentication errors

Authentication is required for all user-facing modes (ASL, Voice, and Letter). The auth flow runs through the Voice service on port 8001.

- Confirm `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set.
- Confirm `SESSION_SECRET` is set identically across all service processes. Without a shared secret, the ephemeral dev fallback generates a per-process key that breaks cross-service session decoding.
- Confirm the authorized redirect URI matches the real browser-visible callback:
  - local direct mode example: `http://127.0.0.1:8001/auth/callback`
  - proxy/same-origin example: `https://your-domain/voice-api/auth/callback`

### ASL or Letter returns 401 after successful login

- Verify `SESSION_SECRET` is set in `.env` and shared by all services — not generated per-process.
- Verify the browser is sending credentials (cookies) on cross-origin requests — check CORS `allow_credentials` and the frontend `credentials: "include"` setting.
- In proxy/tunnel mode, verify the proxy forwards the `Cookie` header to the ASL and Letter backend ports.

### STT or translation is not working

- `POST /api/translate` and `WS /ws/stt` require an authenticated session.
- Confirm microphone permission in the browser.
- Verify Azure Translator credentials for translation and Google STT credentials for speech recognition.

### TTS route exists but playback still fails

- Verify Google TTS credentials and backend logs.
- The route is `POST /api/tts` on the Voice service.

## 5. Admin, Contributor Intake, And Feedback

### Contributor leads or feedback are not showing up

- Submit a test entry through the live Contribute or Home feedback form.
- If you are using SQLite admin persistence, verify that `data/admin.sqlite3` exists.
- If you are using Supabase admin persistence, check the admin service startup logs for `Admin persistence: Supabase`.
- Verify that the Admin service on port `8003` is healthy.
- Remember that public intake is rate-limited by IP with a 10-second cooldown and a 10-per-hour limit.

### Admin dashboard access denied

- Missing or insecure `ADMIN_ACCESS_TOKEN` causes protected admin routes to return `503`.
- A wrong or missing `X-Admin-Token` value causes protected admin routes to return `401`.
- The admin page stores the token in browser session storage, so clearing the tab/session can require re-entry.

### Forwarded client IPs look wrong behind a proxy

- Set `TRUSTED_PROXY=true` if you want the admin service to trust `X-Forwarded-For`.
- `TRUSTED_PROXY=1` is not the code path used by the current implementation.

## 6. Logs And Verification

When the failure is unclear, check the terminal output of the specific service process:

- ASL: model/checkpoint/runtime issues
- Voice: OAuth, session, Google, or Azure issues
- Letter: camera upload or classifier issues
- Admin: token validation, rate limiting, SQLite/Supabase, or SMTP issues

## 7. Supabase

### Profile sync is not working

- Confirm `SUPABASE_ENABLED=true`, `SUPABASE_URL`, and `SUPABASE_SERVICE_ROLE_KEY` are set in `.env`.
- Check the Voice/Auth service logs for Supabase upsert errors after an OAuth callback.
- Confirm the `profiles` table exists in Supabase (apply `docs/sql/supabase_profiles.sql` if not).
- Profile sync is non-blocking — the OAuth login still succeeds even if Supabase is unreachable. Check logs for `Supabase profile sync failed (non-fatal)`.

### Admin data is still going to SQLite

- `SUPABASE_USE_FOR_ADMIN` must be `true` **in addition to** `SUPABASE_ENABLED`.
- Check the Admin service startup logs. Look for `Admin persistence: Supabase` (success) versus `SUPABASE_USE_FOR_ADMIN is set but Supabase is not enabled; using SQLite` or `Supabase admin init failed; falling back to SQLite` (fallback).
- Fix the configuration issue and restart the Admin service.

### Transcript history sync returns `503`

- `/api/transcripts` is backed by the Supabase transcript repository.
- Confirm `SUPABASE_ENABLED=true`, `SUPABASE_URL`, and `SUPABASE_SERVICE_ROLE_KEY` are set in `.env`.
- Confirm the `transcripts` table exists in Supabase (apply `docs/sql/supabase_transcripts.sql` if not).
- `SUPABASE_USE_FOR_ADMIN` is **not** required for transcript storage.
- Local browser history remains available even when backend transcript storage is unavailable.

### `RuntimeError: SUPABASE_ENABLED is true but SUPABASE_URL is empty`

- Set `SUPABASE_URL` in `.env` to the project URL from the Supabase dashboard (Settings > API).
- The same pattern applies for a missing `SUPABASE_SERVICE_ROLE_KEY`.

### Duplicate key / 409 on contributor lead insert

- The `contributor_leads` table has a `UNIQUE` index on `email`. Submitting the same email twice returns an idempotent success response — this is expected behavior, not an error.

### Supabase secrets visible in the browser

- This should not happen. None of the `SUPABASE_*` variables are included in `frontend_app_config` or written to `frontend/runtime-config.js`.
- If you see Supabase credentials in the browser, check for custom code that may have added them to the frontend config. The standard `runtime_config.py` excludes all Supabase fields from the frontend payload.
